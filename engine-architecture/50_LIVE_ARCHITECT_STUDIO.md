# 50 — Live Architect Studio & Dormant World Runtime

**Status:** Architecture. Amends the frozen baseline per explicit user authorization (2026-08-04). This is the in-world collaborative editor and the dormant-universe laboratory.
**Date:** 2026-08-04

---

## 0. What this document is for

The Grand Architect Control Plane (doc 43) gives the AI inspection and control capabilities. It does not, by itself, give the user and the AI a shared in-world surface where they can co-create the world while playing, converse about intent, select any object or region, preview modifications, and apply them transactionally.

This document specifies that surface: the **Live Architect Studio** — a first-class engine subsystem embedded inside the running game. It also specifies the **Dormant World Runtime** — the ability to load or generate a world without beginning normal gameplay simulation, so the user and Architect can inspect, reshape, selectively awaken, test, and enter the world without reloading.

The doctrine (AGENTS.md Part 3) says: "Build the engine, not just the brake." The Live Architect Studio is the positive specification of what the editor unlocks — not a gate, but a workspace.

---

## 1. The Live Architect Studio

### 1.1 Three editor modes

The studio has three modes, all operating on the same authoritative world state:

1. **Play Mode** — Normal gameplay. The editor systems remain available but invisible.
2. **Live Architect Mode** — The world continues running while the user and Architect edit it. Useful for placing objects, changing lighting, spawning characters, editing dialogue, modifying terrain, testing encounters, discussing composition while moving through the scene.
3. **Isolated Preview Mode** — The engine forks the selected area or world state into a temporary preview. Required for dangerous changes: large terrain alterations, deleting settlements, changing procgen rules, replacing foundational assets, modifying faction or history state, regenerating populated regions.

Entering Architect Mode must not require leaving or rebuilding the current world.

### 1.2 The edit pipeline

Every nontrivial request follows:

```
User request
  → target resolution (visual grounding)
  → visual highlight
  → clarification when confidence is low
  → structured operation plan
  → preview layer
  → dependency and performance analysis
  → user/AI inspection
  → accept, revise, partially accept, or discard
  → transactional application
```

For trivial actions (spawning a harmless prop), instant application is permitted. Larger operations preview first.

## 2. Semantic visual grounding

The engine cannot rely solely on a VLM guessing what "that tree" or "the thing behind the shrine" means. Every visible object participates in a semantic selection system.

### 2.1 The provenance chain

When the user points at something, the engine resolves:

```
rendered pixels
  → render primitive
  → presentation object
  → runtime entity
  → asset instance
  → source asset
  → owning plugin
  → generated provenance
  → world location
  → editable properties
```

### 2.2 Confidence levels

- **High confidence** — Highlight and proceed to preview.
- **Medium confidence** — Highlight the presumed target and ask for confirmation.
- **Low confidence** — Highlight multiple candidates with labels (A, B, C) or ask the user to point, click, brush, or lasso.

The system **never** silently modifies a guessed target when the request is ambiguous.

### 2.3 Conversational context anchors

After an entity, asset, terrain region, animation, effect, NPC, or UI element is confirmed, subsequent dialogue remains grounded to that target until context is explicitly changed.

## 3. Selection system

### 3.1 Selection tools

- **Direct**: click, shift-click multi-select, hierarchy, by name/type/tag/faction/material/origin, visible instances, connected parts, source asset vs. instance.
- **Spatial**: freeform lasso, screen-space rectangle, 3D volume, sphere, box, cylinder, spline, surface brush, terrain-height range, path corridor, flood-fill connected region.
- **Semantic**: "select every dead tree visible from here," "buildings belonging to this settlement using the old roof set," "terrain patches with navigation problems," "everything generated by the forest-decoration rule."

### 3.2 The SpatialSelection mask

```typescript
interface SpatialSelection {
  id: string;
  shape: SelectionShape;
  worldBounds: Bounds3D;
  surfaceMask?: SurfaceMask;
  volumeMask?: VolumeMask;
  includedEntities: EntityId[];
  includedTerrainChunks: ChunkId[];
  affectedSystems: CapabilityId[];
  falloff: FalloffProfile;
  filters: SelectionFilter[];
  exclusions: ExclusionZone[];
  source: 'brush' | 'lasso' | 'ray' | 'semantic-query' | 'combined';
}
```

A selected region is passed to different plugins: terrain (raise/lower/erode), ecology (populate/thin/age), assets (scatter/align), lighting (probes), audio (ambient regions), navigation (rebuild), simulation (territories/habitats/encounters).

## 4. Operation plans

The AI converts a natural-language request into an inspectable operation plan before execution:

```
TARGET: User spatial selection: selection-882
OBSERVATION:
  - Low environmental density
  - Sparse vertical silhouettes
  - No meaningful landmarks
  - Current navigable combat area: 2,800 m²
OPERATIONS:
  1. Add a ruined minor structure near the western edge.
  2. Scatter 26–40 biome-compatible trees.
  3. Add rocks and ground vegetation with varied density.
  4. Preserve a central 35-meter combat clearing.
  5. Preserve existing player routes and sightline.
  6. Regenerate navigation and ecology metadata.
CONSTRAINTS:
  - Do not move existing quest objects.
  - Do not obstruct the marked path.
  - Use assets compatible with current visual culture.
  - Maintain current performance budget.
OUTPUT: Temporary preview layer.
```

The Architect Console lets the user inspect or edit this plan before execution.

## 5. Transactional commands and semantic history

The editor uses a transactional command system, not direct uncontrolled mutation.

```
Architect Operation
  → transaction
  → semantic diff
  → validation
  → commit to editor history
```

Each operation records: who requested it, the original NL request, resolved targets, selected tools, changed properties, generated assets, affected systems, previous state, new state, validation evidence, provenance, timestamp, undo operation.

### 5.1 Semantic undo

The user can say: "Undo the vegetation from two changes ago, but keep the ruins." This requires semantic history, not a binary snapshot stack.

### 5.2 Named branches

```
Current Valley
├── More mystical
├── More realistic
└── War-damaged version
```

The user walks around inside each version and chooses or merges elements.

## 6. The Dormant World Runtime

There is no separate "editor data" and "game data." One authoritative world state:

```
Authoritative world database
  ├── Dormant editor representation
  ├── Selectively simulated representation
  ├── Fully running game representation
  └── Player-controlled representation
```

### 6.1 World execution states

1. **Generation Freeze** — Engine generates the world, then freezes before simulation history advances. Nothing ages, moves, consumes, fights, travels, dies, or changes unless explicitly previewed.
2. **Dormant Architect Mode** — Renderer and editor active; gameplay simulation stopped. Fly anywhere, edit anything.
3. **Selective Awakening** — Unpause selected NPC, settlement, encounter, region, or individual simulation domain (physics, animation, AI, ecology, economy, weather) without unpausing the whole universe.
4. **Step Simulation** — Advance one render frame, physics tick, AI decision, combat turn, minute, day, year, or run until a selected event occurs.
5. **Full World Simulation** — Everything active per normal relevance and tier rules.
6. **Player Embodiment** — Spawn as normal character, test character, possess an NPC, control a creature, flying camera, Architect avatar, invisible observer.
7. **Temporary Simulation Fork** — Frozen snapshot → fork → selectively awaken → play → discard, partially merge, or preserve as named branch → return to frozen state.

### 6.2 Freeze, fork, test, return

Any test is reproducible:

```
Frozen authoritative snapshot
  ↓
Create temporary test fork
  ↓
Unpause chosen systems
  ↓
Play, observe, debug
  ↓
Choose: discard / preserve selected / merge all / create named branch
  ↓
Return to original frozen state
```

The diff reports: NPCs died, apprentices advanced, shops insolvent, buildings damaged, faction relationships changed, item transfers, navigation failures. The user decides what becomes permanent.

## 7. Architect powers

Architect authority (broader than normal cheats): teleportation, no-clip, flight, invisibility, invulnerability, time control, weather control, daylight control, entity possession, spawn/despawn, terrain manipulation, asset summoning, instant construction, faction/relationship editing, cultivation-realm editing, memory/knowledge inspection, quest-state manipulation, world-law modification, event triggering/cancellation, simulation rewind, branch creation, hidden-state revelation, collision/navigation overlays, performance/dependency overlays.

## 9. Capability self-extension

When a requested result cannot be achieved correctly with current capabilities, the Architect must not silently approximate. It classifies the result as: **production-ready**, **prototype**, **proxy**, **approximation**, or **blocked**.

When a capability is missing, the Architect may propose and create a new engine tool, editor tool, procedural generator, asset pipeline, adapter, or plugin. Development occurs in an isolated workspace and passes typed-contract validation, conformance tests, integration tests, determinism tests, performance budgets, permission review, visual review, undo verification, and sandbox demonstration before registration.

Every AI-created capability becomes a reusable, versioned engine capability — not an untracked one-off script.

## 10. Art-direction conversations

The dialogue is not limited to command-and-response. It has an art-direction conversation mode.

The user says: "I want entering this valley to feel like discovering somewhere sacred, but I don't want obvious glowing fantasy clutter."

The Architect translates into visual principles: restrained palette, strong silhouette framing, sparse supernatural indicators, natural fog, one distant landmark, subtle motion, no dense floating particles, sacredness through composition and age.

Accepted artistic decisions are saved as machine-readable constraints associated with relevant locations, factions, cultures, assets, or systems so future generation respects them.

## 11. Grand Architect initiative modes

- **Silent** — Only respond when addressed.
- **Assistant** — Warn about errors and major conflicts.
- **Collaborator** — Offer design and technical suggestions.
- **Creative Director** — Continuously critique and propose improvements.

In proactive modes, the AI may highlight visual, technical, simulation, performance, or coherence problems and propose improvements, but must preserve user authority and preview consequential changes.

## 12. No-shortcut quality doctrine

The Architect distinguishes:

- **Production solution** — Meets the full requested capability.
- **Prototype** — Tests the concept but is not final.
- **Proxy** — Temporary representation awaiting a finished asset.
- **Approximation** — Uses existing capabilities, differs from requested result.
- **Blocked** — Cannot currently be produced correctly.

It must not label a proxy as complete. Completion evidence includes in-world screenshots, animation tests, deformation tests, topology validation, collision validation, LOD validation, material validation, frame-cost measurements, scale comparison, visual review against the agreed blueprint, and user approval.

## 13. Modular editor studios

The editor is not monolithic. Plugins contribute studios: Terrain, Asset, Character, Animation, VFX, World-Law, Settlement, Faction, NPC, History, Ecology, Dialogue, Quest, Audio, Lighting, Performance, Simulation, Procedural Blueprint. The Architect opens, combines, or extends these workspaces based on the request.

---

## 14. Blueprint-driven assets

Assets retain a procedural blueprint whenever possible. A building preserves: structural footprint, floor count, wall modules, roof grammar, material family, cultural style, weathering, damage state, door/window sockets, interior graph, navigation, collision, decorative placement rules, generation seed. The user can say "make this two floors taller and convert to mountain architecture" and the system regenerates structurally rather than crudely stretching the mesh.
