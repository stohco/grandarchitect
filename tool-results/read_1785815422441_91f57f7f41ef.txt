     8→## 0. What this document is
     9→
    10→This is the implementation order. Seven phases, each with a working thing at the end, each with declared exit criteria, each gated on the previous phase's exits. Phase 0 (the determinism stack) is done — the hash `7fde855dc9d17c7ba11c7d40c1dda10535a10dd269af0b37149104c256213f75` is the proof, on the determinism page, identical in Chrome, Firefox, and Safari. Phases 1 through 6 are the work ahead.
    11→
    12→The doctrine (AGENTS.md Part 3) is the spine of this plan:
    13→
    14→- **"Authorize the smallest end-to-end thing that works."** Each phase ends with a working thing, not a partial thing. Phase 1 ends with a kernel that boots and a plugin that runs. Phase 6 ends with a vertical slice a player can play for an hour.
    15→- **"Ship the working thing before the perfect thing."** The vertical slice (Phase 6) is the load-bearing deliverable. Every prior phase exists to enable it. If a phase's exit criteria are not met, the next phase does not start.
    16→- **"Add exits, not gates."** Each phase has declared exit criteria. The exit is the gate's complement: instead of "you cannot proceed until X," it is "you may proceed once X is demonstrably true." The demonstration is the gate.
    17→- **"State the calendar and the budget."** This document does not name a calendar (that is the project plan's job), but it names the *order* and the *dependencies*. The calendar is the residue of the order and the team's velocity.

    21→## 1. The 16 questions
    22→
    23→### 1.1 The implementation order
    24→
    25→The order is:
    26→
    27→- **Phase 0:** Determinism stack. (DONE.)
    28→- **Phase 1:** Kernel + plugin SDK.
    29→- **Phase 2:** Reference plugins (renderer, physics, terrain, animation, VFX).
    30→- **Phase 3:** Simulation systems (NPC, ecology, economy, history).
    31→- **Phase 4:** Game systems (cultivation, combat, quests).
    32→- **Phase 5:** Content generation (definitions, templates, rules).
    33→- **Phase 6:** Vertical slice (One Mortal Morning).
    34→
    35→Each phase is a layer on the previous. No phase skips ahead. No phase starts before the previous phase's exit criteria are met.
    36→
    37→### 1.2 Phase 0: determinism stack (DONE)
    38→
    39→**What it is.** The `src/lib/determinism/` directory: RNG (xoshiro256** + splitmix64, BigInt-backed), transcendentals (Cody-Waite + minimax polynomials, pure TS), fixed-point (Q32.32, BigInt-backed), serialization (CBOR RFC 8949 deterministic encoding), hash (SHA-256 via crypto.subtle + @noble/hashes), fingerprint (the schema-versioned record of every determinism-affecting component).
    40→
    41→**Exit criteria (met).**
    42→
    43→- The determinism harness at `/public/determinism.html` runs 1000 ticks from a fixed seed and produces a final hash.
    44→- The hash is identical in Chrome (V8), Firefox (SpiderMonkey), and Safari (JavaScriptCore).
    45→- The hash is `7fde855dc9d17c7ba11c7d40c1dda10535a10dd269af0b37149104c256213f75`.
    46→- The fingerprint is recorded and embedded in every save.
    47→- The intermediate checkpoint hashes (every 100 ticks) are also identical across browsers.
    48→
    49→**What it proves.** The century-spanning deterministic simulation is possible in a browser, across engines. This is the foundation; everything else is built on it.
    50→
    51→### 1.3 Phase 1: kernel + plugin SDK
    52→
    53→**What it is.** The `PluginHost` (doc 17 §1.2), the world state store (doc 17 §2), the system scheduler, the event bus, the editor surface registry, the headless API (doc 17 §4), the determinism enforcer (doc 17 §3.2), and the plugin SDK (doc 17 §9). The kernel is itself a plugin (`ga:core`).
    54→
    55→```typescript
    56→// Phase 1 deliverables:
    57→interface Phase1Deliverables {
    58→  kernel: PluginHost;            // the core, itself a plugin
    59→  pluginLoader: PluginLoader;    // manifest resolution, dependency topological sort
    60→  headlessApi: HeadlessApi;      // doc 17 §4
    61→  determinismEnforcer: DeterminismEnforcer;  // doc 17 §3.2
    62→  pluginSdk: {
    63→    types: 'ga:core types package';
    64→    examplePlugin: 'ga:fog (promoted from the determinism prototype)';
    65→  };
    66→  editorShell: 'minimal — tweak panel only';
    67→  testFramework: 'doc 38 — unit + determinism classes only';
    68→}
    69→```
    70→
    71→**Exit criteria.**
    72→
    73→- The kernel boots, loads the `ga:fog` plugin (promoted from the determinism prototype), and runs a system every tick.
    74→- `host.checkpoint()` returns the SHA-256 hash of the full world state.
    75→- Two runs with the same seed + same inputs produce the same hash, in Node mode (doc 38 §1.9).
    76→- The headless API responds to `getParams`, `setParams`, `step`, `screenshot` (placeholder), `save`, `load`.
    77→- The tweak panel renders the `ga:fog` parameters and applies changes in real time.
    78→- The unit-test class and the determinism-test class (single-browser, Node mode) pass.
    79→- The conformance suite (doc 38 §1.5) passes for `ga:fog`.
    80→
    81→**What it enables.** Every subsequent phase can build plugins against a stable host. The determinism contract is enforced, not just hoped for. The headless API is the surface the AI agent (and the test framework) uses.
    82→
    83→### 1.4 Phase 2: reference plugins (renderer, physics, terrain, animation, VFX)
    84→
    85→**What it is.** The five reference plugins that prove the architecture works for real game systems:
    86→
    87→| Plugin | What it does | Precedent |
    88→|---|---|---|
    89→| `ga:renderer` | Three.js WebGPU/WebGL2 renderer. Render passes, shadow maps, post-processing. | Three.js docs, doc 17 §5 |
    90→| `ga:physics` | Jolt WASM wrapper + determinism layer. Rigid body, constraints, broadphase. | doc 21 |
    91→| `ga:terrain` | Terrain mesh, brushes, density painting, biome layers. | doc 36 §1.7 |
    92→| `ga:animation` | Animation graph, state machines, blend trees, IK targets. | doc 36 §1.5 |
    93→| `ga:vfx` | VFX recipe runtime, particle emitters, force fields, ribbon trails. | doc 36 §1.6 |
    94→
    95→**Exit criteria.**
    96→
    97→- `ga:renderer` renders the determinism prototype's scene (the fog + water demo) via the plugin system, not the inlined HTML. Frame time ≤16ms on `desktop-high`.
    98→- `ga:physics` simulates 500 rigid bodies at 60Hz, deterministically. Two runs from the same seed produce the same hash, in Node mode.
    99→- `ga:terrain` renders a 1km × 1km terrain with brushes that write to canonical state. Terrain edits are part of the world hash.
   100→- `ga:animation` plays an animation graph on a skinned mesh. Graph assets are content-addressed.
   101→- `ga:vfx` plays a VFX recipe. Recipes are content-addressed.
   102→- The integration-test class (doc 38 §1.4) passes for every pair of reference plugins.
   103→- The performance-test class (doc 38 §1.7) passes for the `village-morning` scenario on `desktop-high`.
   104→
   105→**What it enables.** The engine can render, simulate physics, paint terrain, animate, and emit VFX. This is the "engine" in the ordinary sense — it can make a scene. Phases 3 and 4 build the *game* on top of it.

   107→### 1.5 Phase 3: simulation systems (NPC, ecology, economy, history)
   108→
   109→**What it is.** The simulation systems that make the world alive:
   110→
   111→| System | What it does | Precedent |
   112→|---|---|---|
   113→| `ga:npc-simulator` | NPC schedules, relationships, qi-state, tier transitions. | doc 17 §6, doc 22 |
   114→| `ga:ecology` | Spirit beasts, herbs, qi topology, food web, seasonal cycles. | doc 14 |
   115→| `ga:economy` | Markets, trade routes, prices, salt licenses, production. | doc 18 |
   116→| `ga:history` | Event recording, demographic aggregation, the S2/S1/S0 tier simulation. | doc 17 §6.2, doc 26 |
   117→
   118→**Exit criteria.**
   119→
   120→- `ga:npc-simulator` runs 200 S4 NPCs + 500 S3 + 5000 S2 within the 5ms sim budget on `desktop-high`. Tier transitions are deterministic.
   121→- `ga:ecology` simulates a 10km × 10km region's ecology at S2 aggregate, with deterministic seasonal cycles.
   122→- `ga:economy` runs a market simulation with 50 goods, 10 villages, deterministic price evolution.
   123→- `ga:history` aggregates the century-timescale simulation: 1000 years of demography in headless mode, with the S1/S0 tiers. The 1000-year hash is reproducible (this is the "century-absence test" of doc 07 §6.1).
   124→- The determinism-test class passes for each system, in Node mode.
   125→- The conformance suite passes for each system.
   126→
   127→**What it enables.** The world is alive: NPCs have schedules, ecologies cycle, economies fluctuate, history accumulates. The player can walk through a world that is doing things without them.

   129→### 1.6 Phase 4: game systems (cultivation, combat, quests)
   130→
   131→**What it is.** The game systems the player directly interacts with:
   132→
   133→| System | What it does | Precedent |
   134→|---|---|---|
   135→| `ga:cultivation` | Cultivation state machine, realm transitions, tribulation, deviation. | docs 15, 20, 27 |
   136→| `ga:combat` | Combat grammar, frame data, qi reservoir, injury model. | doc 13 |
   137→| `ga:quests` | Quest state machines, triggers, consequences. | doc 26 |
   138→
   139→**Exit criteria.**
   140→
   141→- `ga:cultivation` models the mortal → Qi Condensation → Foundation → Core Formation realm ladder. Realm transitions are deterministic events.
   142→- `ga:combat` runs the combat grammar (doc 13) with frame data and qi reservoir. Two runs with the same inputs produce the same combat outcomes.
   143→- `ga:quests` runs quest state machines with triggers and consequences. Quest state is part of the canonical state hash.
   144→- The integration-test class passes for `ga:combat` + `ga:cultivation` + `ga:npc-simulator`.
   145→- The conformance suite passes for each system.
   146→
   147→**What it enables.** The player can cultivate, fight, and pursue quests. The game loop closes: the player has something to do, the world responds, the consequences persist.

   151→**What it is.** The content authoring and generation systems:
   152→
   153→| System | What it does | Precedent |
   154→|---|---|---|
   155→| `ga:definitions` | The definition registry, patch system, conflict resolution. | doc 36 §1.8 |
   156→| `ga:templates` | The template system, instantiation, parameter binding. | doc 36 §1.9 |
   157→| `ga:rules` | The rule engine, predicate evaluation, effect dispatch. | doc 36 §1.10 |

   162→**Exit criteria.**
   163→
   164→- `ga:definitions` loads canon definitions from lore, applies patches from mods, and surfaces conflicts in the editor.
   165→- `ga:templates` instantiates a template with a seed and produces a deterministic entity set.
   166→- `ga:rules` evaluates a rule's predicate and dispatches its effect, deterministically.
   167→- `ga:gen-settlement` generates Wang Family Bend from the lore (doc 04) and a seed, deterministically. Two runs from the same seed produce the same village, in Node mode.
   168→- `ga:gen-npc` generates the named NPCs of Wang Family Bend (doc 34).
   169→- The world-generator editor (doc 36 §1.4) drives the generators with seed + parameters and previews output.
   170→- The determinism-test class passes for each generator.
   171→
   172→**What it enables.** The world is generated from the lore. The engine's claim — "the lore documents ARE the generator configuration" (doc 17 §8.1) — is now demonstrably true.

   174→### 1.8 Phase 6: vertical slice (One Mortal Morning)
   175→
   176→**What it is.** The vertical slice: a playable hour in Wang Family Bend, on the morning the protagonist's mortal life ends and their cultivation life begins. The smallest end-to-end working product (per AGENTS.md Part 3).
   177→
   178→```typescript
   179→interface VerticalSlice {
   180→  // The scenario: one mortal morning in Wang Family Bend
   181→  scenario: 'one-mortal-morning';
   182→  // The playtime target: 1 hour
   183→  targetPlaytimeMinutes: 60;
   184→  // The first verb: ? (the design corpus says this must be defined before
   185→  // the vertical slice can ship — doc 28 names the village in medias res)
   186→  firstVerb: 'to-be-defined-in-doc-28';
   187→  // The systems exercised (all must be online)
   188→  systems: [
   189→    'ga:renderer', 'ga:physics', 'ga:terrain', 'ga:animation', 'ga:vfx',
   190→    'ga:npc-simulator', 'ga:ecology', 'ga:economy', 'ga:history',
   191→    'ga:cultivation', 'ga:combat', 'ga:quests',
   192→    'ga:definitions', 'ga:templates', 'ga:rules',
   193→    'ga:gen-settlement', 'ga:gen-npc', 'ga:gen-ecology',
   194→  ];
   195→  // The exit: a player can play for an hour, save, reload, and continue.
   196→  exit: 'playable-end-to-end';
   197→}
   198→```
   199→
   200→**Exit criteria.**
   201→
   202→- A player can launch the engine, generate Wang Family Bend from a seed, and walk through it for an hour.
   203→- The first verb (defined in doc 28) is implemented and feels good (the doctrine: "Design for joy first").
   204→- The player can save and reload; the save loads in Chrome, Firefox, and Safari with the same fingerprint.
   205→- The frame budget holds (p95 ≤ 16ms on `desktop-high`).
   206→- The canonical memory holds (≤ 768 MiB).
   207→- The determinism contract holds (the save's hash reproduces in a headless re-run).
   208→- The mod system works: a content mod (a spirit-fox pack) can be installed and adds a spirit fox to the village.
   209→- The crash recovery works: killing the tab mid-play and reopening offers the checkpoint restore.
   210→- The performance test passes for `one-mortal-morning` on `desktop-high`.
   211→
   212→**What it enables.** The doctrine's load-bearing deliverable: "A mortal village that runs in a browser for one hour, with one verb that feels good" (AGENTS.md Part 3). If this ships and feels hollow, the doctrine says "you have learned the most important thing you could learn — and you have learned it now, not after another year of governance."

   251→The graph is linear: each phase depends on the previous. There is no parallelism in the *order* (Phase 3 cannot start before Phase 2 ends), but there is parallelism *within* a phase (the five reference plugins in Phase 2 can be built in parallel; the four simulation systems in Phase 3 can be built in parallel).
   252→
   253→### 1.10 Within-phase parallelism
   254→
   255→| Phase | Parallel tracks |
   256→|---|---|
   257→| 1 | (sequential — the kernel is one piece) |
   258→| 2 | `ga:renderer`, `ga:physics`, `ga:terrain`, `ga:animation`, `ga:vfx` (5 tracks) |
   259→| 3 | `ga:npc-simulator`, `ga:ecology`, `ga:economy`, `ga:history` (4 tracks) |
   260→| 4 | `ga:cultivation`, `ga:combat`, `ga:quests` (3 tracks) |
   261→| 5 | `ga:definitions`, `ga:templates`, `ga:rules`, `ga:gen-settlement`, `ga:gen-npc`, `ga:gen-ecology` (6 tracks) |
   262→| 6 | (sequential — the vertical slice integrates everything) |
   263→
   264→The parallel tracks within a phase are independent: each can be built, tested, and merged without blocking the others. The phase ends when all tracks meet their exit criteria.
   265→
   266→### 1.11 Cross-phase dependencies (the fine print)
   267→
   268→Some Phase N+1 work depends on specific Phase N deliverables:
   269→
   270→- Phase 3's `ga:npc-simulator` depends on Phase 2's `ga:animation` (NPCs need to animate).
   271→- Phase 3's `ga:ecology` depends on Phase 2's `ga:terrain` (ecology lives on terrain).
   272→- Phase 4's `ga:combat` depends on Phase 2's `ga:physics` (combat uses physics for hit detection) and Phase 3's `ga:npc-simulator` (combat affects NPCs).
   273→- Phase 5's `ga:gen-npc` depends on Phase 3's `ga:npc-simulator` (the generator produces NPC entities the simulator consumes).
   274→- Phase 6 depends on everything.
   275→
   276→These dependencies are why the phases are ordered, not parallel. The within-phase parallelism is real; the cross-phase parallelism is limited to non-dependent work.
   277→
   278→### 1.12 What is explicitly deferred?
   279→
   280→The doctrine (AGENTS.md Part 1) says "Avoid speculative abstractions." The following are deferred because they are speculative until the vertical slice proves the engine works:
   281→
   282→- **The Mahayana Law Author surface** (doc 17 §7.4). This is the endgame meta-editor. It is designed but not built; it depends on the engine being shippable first.
   283→- **The full mod ecosystem** (doc 35). The vertical slice needs only one content mod to prove the mod system works; the full registry, signing infrastructure, and curated portal are post-slice.
   284→- **The cross-century simulation** (1000-year headless). Phase 3's `ga:history` proves the 1000-year hash is reproducible; the *gameplay* of century-spanning play is post-slice.
   285→- **The full determinism debugger UI** (doc 37 §1.6). The backend (divergence finder) is built in Phase 1; the editor UI is built when the first real divergence needs debugging.
   286→- **Mobile and `desktop-low` tier support.** The vertical slice targets `desktop-high`. Lower tiers are post-slice; the tier scaling (doc 39 §6) is designed but not calibrated until the slice runs.

   312→### 1.15 What is the calendar?
   313→
   314→The doctrine (AGENTS.md Part 3) says "State the calendar and the budget." What this document names is the *order* and the *dependencies*. The calendar is: Phase 1 starts when staffing is named; each subsequent phase starts when the previous phase's exit criteria are met. The honest answer about how long that takes is the project plan's, not this document's.

   379→## 3. Failure cases (what blocks a phase?)
   380→
   381→| Blocker | Detection | Recovery | Impact |
   382→|---|---|---|---|
   383→| Phase 1 exit criteria not met (kernel unstable) | Test framework | Do not start Phase 2; fix Phase 1 | Phase 2 delayed |
   384→| Cross-browser determinism breaks (a Phase 2 plugin uses Math.sin) | Determinism test | Block phase exit; fix the plugin | Phase exit delayed |
   385→| Performance budget cannot be met (Phase 3 NPC sim too slow) | Performance test | Reduce entity budget or optimize | Phase exit delayed, or budget revised |
   386→| Asset pipeline cannot produce required assets (Blender version drift) | Asset pipeline build | Pin Blender version; rebuild assets | Phase 2 or 5 delayed |
   387→| Lore-to-schema parser fails on a lore document | Parser test | Fix parser or revise lore | Phase 5 delayed |
   388→| Vertical slice feels hollow (first verb not fun) | Playtest | Revise the first verb; loop (the doctrine's loop) | Phase 6 delayed — this is the doctrine's predicted lesson |
   389→| Staffing insufficient for parallel tracks | Project plan | Serialize the tracks; extend calendar | Phase duration extends |
   390→| A phase's exit criteria are ambiguously met | Test framework | Refine the criteria to be binary | Phase cannot exit until criteria are unambiguous |

   394→## 4. Rejected alternatives
   395→
   396→- **Parallel phases (skip ahead).** Rejected: the doctrine (AGENTS.md Part 1) says "Grow the system in layers. Start from the smallest version that works end to end, and add each new capability on top of a product that already works." Skipping ahead produces a product that does not work end to end at any intermediate point.
   397→
   398→- **Big-bang integration (build everything, integrate at the end).** Rejected: this is the doctrine's explicit failure mode. The vertical slice is the integration point; every prior phase is a partial integration that already works.
   399→
   400→- **Phase 6 (vertical slice) before Phase 5 (content generation).** Rejected: the vertical slice needs Wang Family Bend, which needs the generators. Building the slice without the generators means hand-placing the village, which is not the engine's claim ("the lore documents ARE the generator configuration").
   401→
   402→- **Phase 5 before Phase 3 (simulation systems).** Rejected: the generators produce entities the simulation systems consume. Building generators first produces entities that nothing simulates.
   403→
   404→- **Deferring the determinism contract to "later."** Rejected: this is the engine's defining property. Phase 0 is done first precisely because it is the foundation; deferring it would mean building on sand.
   405→
   406→- **Deferring the mod system to post-slice.** Rejected for the *system*, accepted for the *ecosystem*. The mod system (sandbox, signing, conflict resolution) is built in Phase 1 (kernel) and exercised in Phase 6 (one content mod). The full registry and portal are post-slice.
   407→
   408→- **Building all reference plugins (Phase 2) before any simulation (Phase 3).** Accepted: this is the plan. The reference plugins are the substrate the simulation runs on. Building simulation before rendering would mean simulating blind.
   409→
   410→- **Calibrating budgets (doc 39) before the reference plugins exist.** Rejected: budgets are calibrated against measurements. The Phase 1 budget is provisional; the Phase 2 budget is calibrated; the Phase 6 budget is final. Calibrating earlier would be guessing.
   411→
   412→- **A "research mode" gate that blocks production until "measured evidence" is provided.** Rejected: this is the doctrine's explicit failure mode (AGENTS.md Part 3: "A binary 'research / production' gate with a 'measured evidence required' exit is a closed loop if measurement requires code"). The vertical slice is the research artifact that produces the measured evidence. There is no separate research mode; every phase's exit criteria are measured.
   413→
   414→- **Skipping the playtest for the vertical slice.** Rejected: the doctrine (Part 3) says "Design for joy first." The playtest is the measurement of joy. A slice that is not playtested is a slice that has not met its exit criteria.
