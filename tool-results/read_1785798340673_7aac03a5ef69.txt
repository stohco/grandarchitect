    11→## 0. What this document is
    12→
    13→The engine is a plugin host (doc 02, doc 03). Every system — renderer, physics, NPC simulator, ecology, economy, history, cultivation — is a plugin. A human designer can inspect and tune any of them through the editor suite (doc 36). The **Grand Architect Control Plane** is the equivalent surface for an authorized AI: a control plane that lets an AI inspect, understand, test, modify, and extend every subsystem with the same degree of access as a senior engine engineer, but under a security boundary and an autonomy model that protects the player's save, the determinism contract, and the project's integrity.
    14→
    15→The doctrine (AGENTS.md Part 3) says: "Build the engine, not just the brake." The control plane is the engine. It is not a watchdog over an AI that is otherwise locked out; it is the surface through which the AI does its work. The brake (security, audit, autonomy levels, transactional rollback) is paired with the engine (inspection, editing, execution, explanation) — each gate has a corresponding capability, and each capability has a corresponding gate.
    16→
    17→The doctrine also says: "Do not confuse the apparatus with the work." The control plane is apparatus. Its purpose is to let the AI produce **experience**: a working vertical slice, a feel that lands, a moment a player remembers. Every page of control-plane specification in this document and its companion docs (44-49) is justified by the experience it enables, not by the governance it adds.
    18→
    19→This document defines the overall architecture. The companion documents drill into specifics: the tool/protocol (44), the visual observation channel (45), the change validation/promotion pipeline (46), the research and dependency acquisition broker (47), the security model and audit trail (48), and the machine-readable capability and decision graph (49).

    23→## 1. The three communication channels
    24→
    25→The control plane is not one channel; it is three. Each channel is optimized for a different communication pattern. Confusing the channels — using the command channel for events, or the browser channel for state mutations — produces fragile integrations and lost messages. The three channels are:
    26→
    27→```
    28→┌────────────────────────────────────────────────────────────────────────┐
    29→│                  GRAND ARCHITECT CONTROL PLANE                          │
    30→│                                                                        │
    31→│   ┌──────────────┐   ┌──────────────────┐   ┌──────────────────────┐  │
    32→│   │   WEBHOOK    │   │  COMMAND CHANNEL │   │   BROWSER / VLM      │  │
    33→│   │  (async)     │   │  (live, ordered) │   │   (observation)      │  │
    34→│   └──────┬───────┘   └────────┬─────────┘   └──────────┬───────────┘  │
    35→│          │                    │                        │              │
    36→│          │  events the        │  commands the AI       │  pixels and  │
    37→│          │  engine pushes     │  issues; results it    │  buffers the │
    38→│          │  to the AI when    │  receives synchronously│  AI inspects │
    39→│          │  something happens │  or as task results    │  visually    │
    40→│          │                    │                        │              │
    41→│          v                    v                        v              │
    42→│   ┌────────────────────────────────────────────────────────────────┐  │
    43→│   │                   ARCHITECT GATEWAY                            │  │
    44→│   │      (the security boundary; see section 3)                    │  │
    45→│   └────────────────────────────────────────────────────────────────┘  │
    46→│                              │                                         │
    47→│                              v                                         │
    48→│   ┌────────────────────────────────────────────────────────────────┐  │
    49→│   │                   ENGINE PLUGIN HOST                            │  │
    50→│   │   (kernel, plugins, simulation, renderer, persistence)         │  │
    51→│   └────────────────────────────────────────────────────────────────┘  │
    52→└────────────────────────────────────────────────────────────────────────┘
    53→```
    54→
    55→### 1.1 The webhook channel (async events)
    56→
    57→The webhook channel carries **engine-to-AI** notifications. When something the AI should know about happens — a generation completed, a determinism checkpoint mismatched, a test failed, a build finished, a new save was written, a performance threshold was breached — the engine POSTs a signed event to a configured webhook URL. The AI reacts on its own schedule.
    58→
    59→```typescript
    60→interface WebhookEnvelope {
    61→  /** The event type, namespaced: 'engine.checkpoint.Mismatch', 'build.Completed'. */
    62→  type: string;
    63→  /** ISO 8601 timestamp. */
    64→  timestamp: string;
    65→  /** The engine session that emitted this event. */
    66→  sessionId: string;
    67→  /** The engine tick at which the event was emitted, if applicable. */
    68→  tick?: bigint;
    69→  /** The event payload, CBOR-serializable. */
    70→  payload: unknown;
    71→  /** HMAC-SHA256 over (type, timestamp, sessionId, payload) using the shared webhook secret. */
    72→  signature: string;
    73→  /** A monotonic sequence number per session, for ordering and dedup. */
    74→  seq: number;
    75→}
    76→```
    77→
    78→The webhook is **fire-and-forget from the engine's perspective**. The engine does not block on the AI acknowledging the event. If the AI is offline, events queue up to a configured retention (default 24h, max 10k events) and are drained when the AI reconnects. The engine does not retry indefinitely — beyond the retention window, dropped events are dropped, and the AI is expected to reconcile by re-querying state through the command channel.
    79→
    80→The webhook channel is **read-only for the AI**. The AI cannot mutate engine state through it. It can only react.
    81→
    82→### 1.2 The persistent command channel (live control)
    83→
    84→The command channel is the AI's hands. It is a persistent, ordered, request-response channel over WebSocket (primary) or JSON-RPC over HTTP (fallback). Every tool call the AI makes — inspect a chunk, patch a definition, run a test, launch a playtest — flows through this channel. The channel is **persistent** because some operations (long simulations, year-long playthroughs, multi-hour playtests) take longer than an HTTP request can reasonably stay open, and the AI needs to be able to issue follow-up commands, poll for results, and cancel in-flight work.
    85→
    86→```typescript
    87→interface CommandRequest {
    88→  /** A ULID, used to match the response. */
    89→  requestId: string;
    90→  /** The session this command belongs to. */
    91→  sessionId: string;
    92→  /** The tool name, namespaced: 'engine.describe', 'definition.patch'. */
    93→  tool: string;
    94→  /** The arguments object, validated against the tool's input schema. */
    95→  args: Record<string, unknown>;
    96→  /** The autonomy level the AI is asserting for this call (see section 5). */
    97→  assertedAutonomy: AutonomyLevel;
    98→  /** A capability token proving the AI is permitted to call this tool at this autonomy. */
    99→  capabilityToken: string;
   100→  /** A deadline (ms from issue). The engine refuses to start work past the deadline. */
   101→  deadlineMs: number;
   102→}
   103→
   104→interface CommandResponse {
   105→  requestId: string;
   106→  status: 'ok' | 'error' | 'pending' | 'cancelled';
   107→  /** Present when status is 'ok' or 'error'. */
   108→  result?: unknown;
   109→  error?: { code: string; message: string; details?: unknown };
   110→  /** For long-running operations, a handle the AI can poll or cancel. */
   111→  asyncHandle?: string;
   112→  /** The audit record for this call (see doc 48). */
   113→  audit: AuditRecord;
   114→}
   115→```
   116→
   117→The channel's ordering guarantees: commands from a single session are processed in issue order. Commands from different sessions are processed concurrently. The engine may rate-limit a session that exceeds its declared budget (see doc 44 §6).
   118→
   119→The command channel is **the only channel through which the AI mutates engine state**. The webhook channel is read-only; the browser channel can drive input (for playtests) but cannot directly mutate simulation state — input it injects becomes a command in the input log, processed through the normal command path.
   120→
   121→### 1.3 The browser/VLM channel (visual observation)
   122→
   123→The browser/VLM channel is the AI's eyes. It carries **synchronized multimodal inspection packages** — RGB frames, depth buffers, object-ID buffers, surface normals, motion vectors, collision wireframes, navigation overlays, voxel/density visualizations, lighting buffers, entity labels, performance heat maps, scene graph fragments, physics contact lists, selected-object component data, and current engine logs — that let the AI see what the engine is rendering and why. The browser channel is detailed in doc 45.
   124→
   125→The browser channel is **bidirectional but asymmetric**: the AI receives rich visual telemetry (high bandwidth, often) and can issue low-rate input events (mouse moves, key presses, click targets) to drive a playtest. But the AI cannot use the browser channel to mutate engine state directly — input it injects becomes a command, processed through the command channel's audit path.
   126→
   127→### 1.4 Why three channels, not one
   128→
   129→A single channel — "everything is a tool call" — was the obvious first design. It was rejected for three reasons:
   130→
   131→1. **Bandwidth and polling.** Visual telemetry is high-bandwidth and stateful. Polling it through a request-response channel wastes bandwidth and adds latency. A dedicated observation channel lets the engine push frames when the scene changes, not when the AI asks.
   132→2. **Liveness.** Engine events (a checkpoint mismatch, a build failure) need to reach the AI even when the AI is not actively polling. A webhook channel is the standard pattern for this; pretending a request-response channel is also an event channel produces contortions (long-poll, server-sent events bolted on).
   133→3. **Separation of concerns.** The audit story for a state mutation (every call recorded, every change diffed, every approval tracked) is different from the audit story for a frame render (sampled, summarized, retained briefly). One channel with one audit model would over-audit observation and under-audit control.

   137→## 2. The Architect Gateway
   138→
   139→The Architect Gateway is the single chokepoint through which all three channels pass. It is the security boundary between the AI and the engine. The engine's PluginHost never accepts a connection from an AI directly; it accepts connections only from the Gateway, which has authenticated the AI, verified its capability tokens, enforced its autonomy level, and logged the call.
   140→
   141→```
   142→┌─────────────┐         ┌────────────────────────────┐         ┌──────────────┐
   143→│             │  web-   │                            │  plain   │              │
   144→│   AI agent  │  hook   │       ARCHITECT GATEWAY    │  WSS /   │   PluginHost │
   145→│  (external) │────────>│                            │  JSON-   │   (engine)   │
   146→│             │  WSS /  │  • TLS termination         │  RPC     │              │
   147→│             │  JSON-  │  • session authentication  │-------->│              │
   148→│             │  RPC    │  • capability token check  │         │              │
   149→│             │         │  • autonomy level enforce  │         │              │
   150→│             │         │  • rate limiting           │         │              │
   151→│             │         │  • audit log write         │         │              │
   152→│             │         │  • approval routing        │         │              │
   153→│             │         │  • tool schema validation  │         │              │
   154→│             │         │  • webhook signing         │         │              │
   155→│             │         │  • VLM session multiplex   │         │              │
   156→└─────────────┘         └────────────────────────────┘         └──────────────┘
   157→```
   158→
   159→```typescript
   160→interface ArchitectGateway {
   161→  /** Authenticate an AI principal; return a session. */
   162→  authenticate(credentials: AICredentials): Promise<ArchitectSession>;
   163→  /** Validate a command request against the session's capabilities and autonomy. */
   164→  authorize(req: CommandRequest, session: ArchitectSession): AuthorizationResult;
   165→  /** Forward an authorized command to the engine; return the response. */
   166→  forward(req: CommandRequest, session: ArchitectSession): Promise<CommandResponse>;
   167→  /** Emit a webhook to the AI's registered endpoint. */
   168→  emitWebhook(envelope: WebhookEnvelope): Promise<void>;
   169→  /** Open a VLM observation stream (see doc 45). */
   170→  openVlmStream(session: ArchitectSession, spec: VlmStreamSpec): Promise<VlmStream>;
   171→  /** Look up the audit trail for a session, tool, or entity. */
   172→  queryAudit(filter: AuditFilter): Promise<AuditRecord[]>;
   173→}
   174→
   175→interface ArchitectSession {
   176→  sessionId: string;
   177→  principalId: string;             // which AI identity (see section 4)
   178→  role: ArchitectRole;
   179→  autonomy: AutonomyLevel;          // current max autonomy (see section 5)
   180→  capabilities: string[];           // tool IDs this session may call
   181→  issuedAt: string;
   182→  expiresAt: string;                // short-lived (default 15 min)
   183→  renewalToken: string;             // to extend before expiry
   184→}
   185→```
   186→
   187→The Gateway is **stateless across restarts** except for its audit log (durable) and its session cache (rebuildable from the audit log). It does not hold engine state. It can be restarted without losing the engine; the AI loses its session, reconnects, and resumes.
   188→
   189→The Gateway runs in a **separate process** from the engine, on the same host (in dev) or a sidecar (in production). It is the only network endpoint the AI is permitted to reach. The engine's PluginHost listens on a Unix domain socket (or a localhost-only TCP port) that the Gateway proxies to.
   190→
   191→### 2.1 Gateway failure modes
   192→
   193→- **Gateway crash.** The AI's session is lost; the engine continues running. The AI reconnects, re-authenticates, and resumes. In-flight async commands are orphaned; the engine cancels them after a heartbeat timeout (default 30s) and reports cancellation in the audit log.
   194→- **Gateway desync from engine.** If the Gateway's session cache diverges from the engine's view (e.g., the engine evicted a session for memory pressure), the Gateway's next forward fails with `SessionUnknown`. The AI re-authenticates. The audit log reconciles.
   195→- **Gateway compromise.** The Gateway holds the webhook secret and the session signing key, but not the player's save (that lives in the engine's persistence layer, encrypted at rest with a key the Gateway never sees). A compromised Gateway can issue authorized commands but cannot read saves directly. The audit log detects anomalous command patterns. See doc 48 §5 for incident response.
   196→- **Gateway replay attack.** A captured command cannot be replayed because each command carries a `capabilityToken` bound to the session and the `assertedAutonomy`, and the token is single-use for state-mutating tools.

   200→## 3. The architect roles
   201→
   202→The control plane is not one AI; it is a roster of specialized roles. Each role has its own capability set, its own autonomy defaults, and its own audit profile. The same underlying AI model may serve multiple roles in a small project; in a larger one, different model instances (or different providers) fill different roles. The role is **asserted at session establishment** and **enforced by the Gateway** — a session scoped to the Reviewer role cannot call Implementer tools, even with a stolen token.
   203→
   204→```typescript
   205→type ArchitectRole =
   206→  | 'Architect'              // the coordinator; routes work, sets autonomy
   207→  | 'Researcher'             // doc/paper/GitHub research; see doc 47
   208→  | 'Implementer'            // writes definitions, templates, code; patches plugins
   209→  | 'Reviewer'               // independent critique; see section 6
   210→  | 'VlmPlaytester'          // browser/VLM observation and playtesting; see doc 45
   211→  | 'PerformanceAuditor'     // benchmarks, frame timing, memory budgets
   212→  | 'SimulationAuditor'      // determinism, replay, save/load correctness
   213→  | 'SecurityReviewer';      // permissions, dependencies, attack surface; see doc 48
   214→
   215→interface RoleProfile {
   216→  role: ArchitectRole;
   217→  /** Tools this role may call (subset of the tool registry). */
   218→  allowedTools: string[];
   219→  /** Default autonomy ceiling — the role cannot assert above this without escalation. */
   220→  autonomyCeiling: AutonomyLevel;
   221→  /** Whether this role may initiate approval requests to the human operator. */
   222→  mayEscalate: boolean;
   223→  /** Whether this role's outputs require independent review before promotion. */
   224→  requiresReview: boolean;
   225→}
   226→```
   227→
   228→| Role | Allowed tool families | Autonomy ceiling | May escalate | Requires review |
   229→|---|---|---|---|---|
   230→| Architect | All (coordination only — does not write code) | Branch | Yes | No (it coordinates reviews) |
   231→| Researcher | Inspection, Research (doc 47) | Sandbox | Yes | Yes |
   232→| Implementer | Inspection, Controlled Editing, Execution | Branch | Yes | Yes |
   233→| Reviewer | Inspection, Explanation, Critique | Preview | No | N/A |
   234→| VlmPlaytester | Inspection, VLM tools (doc 45), Playtest | Preview | Yes | Yes |
   235→| PerformanceAuditor | Inspection, profiler.capture, benchmark.run | Preview | No | Yes |
   236→| SimulationAuditor | Inspection, simulation.runYears, replay tools | Preview | No | Yes |
   237→| SecurityReviewer | Inspection, audit queries, dependency inspect | Preview | Yes | Yes |
   238→
   239→The separation is **enforced, not advisory**. The doctrine (AGENTS.md Part 3) says: "Exhibit reviewer voices; do not self-certify." The Architect role cannot approve its own work; the Implementer role cannot ship without a Reviewer's signature. The role boundary is the structural enforcement of that doctrine.
   240→
   241→### 3.1 The Architect role in particular
   242→
   243→The Architect is the coordinator. It does not write code; it routes work, sets the autonomy level for a task, picks which role handles which subtask, and presents the final result to the human operator (or commits autonomously if the autonomy level permits). The Architect is the only role that can change another session's autonomy level, and only via a documented escalation path (section 5).
   244→
   245→### 3.2 Why eight roles
   246→
   247→The doctrine warns against governance apparatus that grows while work does not. Eight roles is the minimum that satisfies "do not self-certify" without producing a meeting room: each role either produces work (Implementer, Researcher, VlmPlaytester) or audits work someone else produced (Reviewer, PerformanceAuditor, SimulationAuditor, SecurityReviewer), with the Architect as the non-writing coordinator. Fewer roles collapse the producer/auditor separation; more roles add coordination cost without adding new perspective.

   251→## 4. The self-improvement loop (16 steps)
   252→
   253→The control plane's purpose is to let the AI improve the engine. "Improve" means: identify a gap, propose a change, implement it, validate it, and commit or roll back. The loop below is the canonical 16-step sequence. Not every step is taken on every change; some steps are no-ops for trivial work. But the loop is the contract — the AI may not skip a step silently, and the audit log records which steps were taken, which were skipped (and why), and which produced evidence.
   254→
   255→```
   256→┌─────────────────────────────────────────────────────────────────────────┐
   257→│                  THE SELF-IMPROVEMENT LOOP (16 STEPS)                    │
   258→│                                                                         │
   259→│   1. Observe        — read engine state, watch a frame, query a system   │
   260→│   2. Compare        — diff current state against desired capability      │
   261→│   3. Diagnose       — identify the root cause of the gap                 │
   262→│   4. Search         — query the World Oracle (doc 49) for prior art      │
   263→│   5. Determine      — decide: fix, extend, or replace?                   │
   264→│   6. Research       — external sources, candidate deps (doc 47)          │
   265→│   7. Propose        — write the change as a Proposal (typed)             │
   266→│   8. Evaluate       — Reviewer + auditors review the Proposal            │
   267→│   9. Implement      — produce the patch in an isolated workspace         │
   268→│  10. Test           — unit + integration (doc 46)                        │
   269→│  11. Simulate       — run years of simulation; check invariants          │
   270→│  12. Benchmark      — frame timing, memory, determinism hash             │
   271→│  13. Playtest       — VLM playtester plays the affected scene            │
   272→│  14. Critique       — independent Reviewer tries to falsify              │
   273→│  15. Present        — semantic diff + evidence to human or Architect     │
   274→│  16. Commit/Rollback — promote to release, or revert and record why      │
   275→└─────────────────────────────────────────────────────────────────────────┘
   276→```
   277→
   278→### 4.1 The 16 steps, in detail
   279→
   280→```typescript
   281→type SelfImprovementStep =
   282→  | 'Observe'        | 'Compare'     | 'Diagnose'    | 'Search'
   283→  | 'Determine'      | 'Research'    | 'Propose'     | 'Evaluate'
   284→  | 'Implement'      | 'Test'        | 'Simulate'    | 'Benchmark'
   285→  | 'Playtest'       | 'Critique'    | 'Present'     | 'CommitOrRollback';
   286→
   287→interface StepRecord {
   288→  step: SelfImprovementStep;
   289→  /** Which role executed this step. */
   290→  role: ArchitectRole;
   291→  /** Timestamps. */
   292→  startedAt: string;
   293→  completedAt: string;
   294→  /** The autonomy level asserted for this step. */
   295→  autonomy: AutonomyLevel;
   296→  /** Tool calls made during this step (references into the audit log). */
   297→  toolCalls: string[];
   298→  /** Artifacts produced (proposal, patch, benchmark report, critique, etc.). */
   299→  artifacts: ArtifactRef[];
   300→  /** The outcome. */
   301→  outcome: 'proceed' | 'loop-back' | 'abort';
   302→  /** If loop-back, which step to return to and why. */
   303→  loopBackTo?: SelfImprovementStep;
   304→  loopBackReason?: string;
   305→}
   306→```
   307→
   308→**1. Observe.** The AI inspects engine state through Inspection tools (doc 44 §3). It reads a chunk, queries an entity, captures a frame. The output is a structured observation, not free text.
   309→
   310→**2. Compare.** The AI diffs the observed state against the **desired capability** (doc 49 §1 — the `CapabilityRequirement` interface). The output is a gap statement: "the renderer cannot currently do X; here is what X requires."
   311→
   312→**3. Diagnose.** The AI identifies the root cause. Not "the frame is slow" but "the depth prepass is disabled, causing overdraw in the foliage system." Diagnosis uses Explanation tools (doc 44 §5) to trace effects back to causes.
   313→
   314→**4. Search.** The AI queries the World Oracle (doc 49 §4) for prior art — has this gap been addressed in an architectural decision? In a plugin? In a rejected alternative? Search prevents re-litigating settled decisions.
   315→
   316→**5. Determine.** The AI decides the strategy: fix in place (patch the existing system), extend (add a new system), or replace (deprecate and rewrite). This decision is recorded as a `Determination` artifact and becomes input to the architectural decision ledger (doc 49 §3).
   317→
   318→**6. Research.** If the fix involves external knowledge — an algorithm, a library, a paper — the Researcher role runs the research broker (doc 47). External candidates are inspected, ranked, and either adopted, adapted, ported, or rejected with reason.
   319→
   320→**7. Propose.** The Implementer writes a `Proposal` — a typed document specifying what will change, what will not change, what the acceptance tests are, and what the rollback plan is.
   321→
   322→```typescript
   323→interface Proposal {
   324→  proposalId: string;
   325→  title: string;
   326→  /** The gap this proposal addresses (references a CapabilityRequirement). */
   327→  addressesGap: string;
   328→  /** What will change, in human-readable terms. */
   329→  summary: string;
   330→  /** The affected systems (plugin IDs, capability IDs, definition IDs). */
   331→  affectedSystems: string[];
   332→  /** What explicitly will NOT change. */
   333→  nonGoals: string[];
   334→  /** Acceptance tests — the proposal is not done until these pass. */
   335→  acceptanceTests: AcceptanceTest[];
   336→  /** The rollback plan. */
   337→  rollback: RollbackPlan;
   338→  /** The autonomy level the AI requests for execution. */
   339→  requestedAutonomy: AutonomyLevel;
   340→  /** Research artifacts, if Research was run. */
   341→  research?: ResearchCandidate[];
   342→  /** Estimated work, in role-hours. */
   343→  estimatedEffort: { role: ArchitectRole; hours: number }[];
   344→}
   345→```
   346→
   347→**8. Evaluate.** The Reviewer role (and, depending on the affected systems, the Performance, Simulation, and Security auditors) reviews the Proposal. They may approve, request changes, or reject. The evaluation is a first-person signed record, not a checklist (per the doctrine: "If you ran a review, sign it").
   348→
   349→**9. Implement.** The Implementer produces the patch in an isolated workspace (doc 46 §1). No code reaches the main branch until validation completes.
   350→
   351→**10. Test.** Unit and integration tests run (doc 46 §4). Failures loop back to Implement.
   352→
   353→**11. Simulate.** The Simulation auditor runs `simulation.runYears` against the patched world. Invariants are checked. Determinism is verified by checkpoint hash. Failures loop back to Diagnose.
   354→
   355→**12. Benchmark.** The Performance auditor runs `benchmark.run`. Frame timing, memory, and the determinism hash are compared against baseline. Regressions loop back to Implement.
   356→
   357→**13. Playtest.** The VLM playtester plays the affected scene (doc 45). It looks for visual artifacts, broken interactions, missing feedback. Failures loop back to Implement or Diagnose.
   358→
   359→**14. Critique.** The Reviewer tries to **disprove** the proposal's success — the falsification requirement (doc 46 §3). The critique is signed and quoted in the final presentation.
   360→
   361→**15. Present.** The Architect composes the semantic diff (doc 46 §2) and the evidence (test results, benchmark report, playtest log, critique) into a presentation. The presentation goes to a human operator (for changes above the AI's autonomy) or to the commit step (for changes within autonomy).
   362→
   363→**16. Commit or Rollback.** The change is committed (promoted through the approval pipeline of doc 46) or rolled back (the workspace is discarded, the audit record retains the attempt, the architectural decision ledger records what was learned).
   364→
   365→### 4.2 Skipping steps
   366→
   367→A step may be skipped only if:
   368→
   369→- The step's preconditions are not met (e.g., Research is skipped if the fix is internal).
   370→- The skip is recorded in the audit log with a reason.
   371→- The skip does not violate a role's `requiresReview` flag.
   372→
   373→The Architect role signs the skip. Skipping Test, Simulate, Benchmark, or Critique for a state-mutating change is **forbidden**; the audit log flags the attempt and the Gateway refuses to commit.

   377→## 5. Risk-based autonomy levels
   378→
   379→The AI does not have a single "trust level." It has a per-task, per-session autonomy level that scales with the risk of the change. Low-risk observations are autonomous; high-risk mutations require approval. The seven levels are linearly ordered; each level permits the previous level's actions plus new ones.
   380→
   381→```typescript
   382→type AutonomyLevel =
   383→  | 'Observe'      // 1 — read anything; mutate nothing
   384→  | 'Diagnose'     // 2 — run traces, explain, propose
   385→  | 'Sandbox'      // 3 — modify isolated workspace; cannot touch main
   386→  | 'Preview'      // 4 — run the workspace in a preview build; player cannot see
   387→  | 'Branch'       // 5 — push the workspace to a branch; CI runs
   388→  | 'Integrate'    // 6 — merge the branch to main; main is updated
   389→  | 'Release';     // 7 — ship to players; save migration may run
   390→```
   391→
   392→| Level | What the AI may do | What it still cannot do |
   393→|---|---|---|
   394→| Observe | Inspect any system, capture frames, query state | Mutate anything; propose without sign-off |
   395→| Diagnose | Run explanation traces, write Proposals, search the Oracle | Mutate state; open a workspace |
   396→| Sandbox | Open an isolated workspace; patch definitions, templates, code in the workspace | Run the workspace outside the sandbox; push to a branch |
   397→| Preview | Run the workspace as a preview build; the VLM playtester may play it | Push to a shared branch; integrate to main |
   398→| Branch | Push the workspace to a version-controlled branch; CI runs | Merge to main; release |
   399→| Integrate | Merge the branch to main (with a Reviewer's signature) | Release to players; run save migrations |
   400→| Release | Promote a build to players; run save migrations (with a human's signature for now) | Change the architect system itself; rewrite migrations |
   401→
   402→### 5.1 The autonomy escalation path
   403→
   404→If the AI needs more autonomy than its current session permits, it escalates:
   405→
   406→```typescript
   407→interface EscalationRequest {
   408→  /** The autonomy level requested. */
   409→  requestedAutonomy: AutonomyLevel;
   410→  /** The task that requires the escalation. */
   411→  taskDescription: string;
   412→  /** The Proposal that justifies the escalation. */
   413→  proposalRef: string;
   414→  /** The risk assessment (what could go wrong, what's the mitigation). */
   415→  riskAssessment: RiskAssessment;
   416→  /** Who must approve (computed from the level: 'human' for Release, 'architect' otherwise). */
   417→  approver: 'human' | 'architect';
   418→}
   419→
   420→interface RiskAssessment {
   421→  /** What could go wrong if the AI proceeds at this autonomy. */
   422→  failureModes: { mode: string; severity: 'low' | 'med' | 'high' | 'critical'; mitigation: string }[];
   423→  /** What the AI has already done to reduce the risk. */
   424→  mitigationsApplied: string[];
   425→  /** The blast radius — what systems / saves / players are affected if it goes wrong. */
   426→  blastRadius: string[];
   427→  /** The rollback cost — how hard is it to undo. */
   428→  rollbackCost: 'trivial' | 'minutes' | 'hours' | 'days' | 'irreversible';
   429→}
   430→```
   431→
   432→The Gateway routes the escalation to the approver: the Architect role for levels up to Integrate, a human operator for Release (and for any change touching the architect system itself, save migrations, or permission grants — see doc 48 §3). The approver's decision is recorded in the audit log with the reason.
   433→
   434→### 5.2 Why seven levels, not three
   435→
   436→The doctrine (AGENTS.md Part 3) warns against binary gates. A three-level model ("observe / sandbox / release") either under-trusts the AI (every interesting change needs release-level approval) or over-trusts it (release becomes the default for anything that touches main). Seven levels let the AI make progress at the lowest level that suffices: a Sandbox-level fix that does not need preview does not need preview-level approval; a Preview-level playtest that does not need a branch does not need branch-level approval. Each level is an exit, not a gate (per the doctrine).

   440→## 6. The transactional change process
   441→
   442→A change is not "applied." It is **transacted**. The transactional change process is the sequence of validation steps every state-mutating change must pass before it is committed. The process is the structural enforcement of the doctrine's "Exhibit reviewer voices; do not self-certify": each step is a checkpoint at which the change can fail and be rolled back, with no partial application.
   443→
   444→```
   445→┌────────────────────────────────────────────────────────────────────────┐
   446→│             THE TRANSACTIONAL CHANGE PROCESS                            │
   447→│                                                                        │
   448→│   Snapshot ──> Patch ──> Build ──> Static Validation ──> Unit Tests    │
   449→│                                                                  │      │
   450→│   <─────────────────────────────────────────────────────────────  │  rollback
   451→│                                                                  v      │
   452→│   Integration Tests ──> Deterministic Replay ──> Performance Bench  │
   453→│                                                                        │
   454→│   <──────────────────────────────────────────────────────────────  rollback
   455→│                                                                  v      │
   456→│   Visual Regression ──> Browser/VLM Playtest ──> Independent Critique  │
   457→│                                                                        │
   458→│   <──────────────────────────────────────────────────────────────  rollback
   459→│                                                                  v      │
   460→│   Semantic Diff ──> Approval or Rollback ──> [committed or reverted]  │
   461→└────────────────────────────────────────────────────────────────────────┘
   462→```
   463→
   464→### 6.1 The transactional interface
   465→
   466→```typescript
   467→interface ChangeTransaction {
   468→  transactionId: string;
   469→  /** The Proposal this transaction implements. */
   470→  proposalRef: string;
   471→  /** The autonomy level asserted. */
   472→  autonomy: AutonomyLevel;
   473→  /** The snapshot the transaction started from (for rollback). */
   474→  baselineSnapshot: SnapshotRef;
   475→  /** The current step. */
   476→  currentStep: TransactionalStep;
   477→  /** The full step history, with results. */
   478→  steps: TransactionalStepRecord[];
   479→  /** The final outcome, when the transaction terminates. */
   480→  outcome?: 'committed' | 'rolled-back' | 'aborted';
   481→}
   482→
   483→type TransactionalStep =
   484→  | 'Snapshot'              // 1. capture the baseline (workspace + state + assets)
   485→  | 'Patch'                 // 2. apply the proposed edits
   486→  | 'Build'                 // 3. compile / bundle
   487→  | 'StaticValidation'      // 4. typecheck, lint, schema validation
   488→  | 'UnitTests'             // 5. unit tests
   489→  | 'IntegrationTests'      // 6. integration tests
   490→  | 'DeterministicReplay'   // 7. replay a known-good input log; hash must match
   491→  | 'PerformanceBenchmarks' // 8. frame timing, memory, determinism hash
   492→  | 'VisualRegression'      // 9. compare frames against baseline
   493→  | 'BrowserVlmPlaytest'    // 10. VLM playtester plays the scene
   494→  | 'IndependentCritique'   // 11. Reviewer tries to falsify
   495→  | 'SemanticDiff'          // 12. produce the human-readable diff
   496→  | 'ApprovalOrRollback';   // 13. commit or revert
   497→
   498→interface TransactionalStepRecord {
   499→  step: TransactionalStep;
   500→  startedAt: string;
   501→  completedAt: string;
   502→  status: 'pass' | 'fail' | 'warn' | 'skipped';
   503→  /** The artifact this step produced (test report, benchmark, diff, etc.). */
   504→  artifact?: ArtifactRef;
   505→  /** If the step failed, the failure details. */
   506→  failure?: { code: string; message: string; details?: unknown };
   507→  /** Whether the transaction rolled back as a result. */
   508→  rolledBack?: boolean;
   509→}
   510→```
   511→
   512→### 6.2 What each step proves
   513→
   514→1. **Snapshot.** The baseline. A full capture of the workspace (source tree, build cache, assets), the world state (seed, tick, checkpoint, command log), and the engine fingerprint. Without a snapshot, rollback is impossible.
   515→2. **Patch.** The proposed edits applied. The patch is a typed object — `definition.patch`, `template.create`, `plugin.scaffold` (doc 44 §4) — not free-form text. The Gateway records the patch in the audit log.
   516→3. **Build.** The workspace compiles. A build failure loops back to Patch.
   517→4. **Static Validation.** TypeScript typecheck, ESLint, JSON schema validation against the plugin manifest and definition schemas. Static validation catches whole classes of bugs without running the engine.
   518→5. **Unit Tests.** Each plugin's unit-test class (doc 38 §1.2). Fast (<10s). Failure loops back to Patch.
   519→6. **Integration Tests.** Cross-plugin interactions (doc 38 §1.4). Slower (<60s). Failure loops back to Patch or Diagnose.
   520→7. **Deterministic Replay.** A known-good input log is replayed against the patched engine. The checkpoint hash must match the baseline hash, byte-for-byte, for every checkpoint. A mismatch means the patch broke determinism — this is a hard fail, no override.
   521→8. **Performance Benchmarks.** The `village-morning` scenario (or the scenario named in the Proposal) runs at the target frame rate. Memory stays within budget (doc 39). The determinism hash matches the baseline. A regression >10% on any metric loops back to Implement.
   522→9. **Visual Regression.** The renderer produces frames at defined checkpoints; each is compared against a baseline image. A perceptual difference above threshold (default: 2% of pixels, with anti-aliasing awareness) flags a regression. The VLM playtester can override false positives.
   523→10. **Browser/VLM Playtest.** The VLM playtester (doc 45) plays the affected scene. It looks for visual artifacts, broken interactions, missing feedback. The playtest log is the artifact.
   524→11. **Independent Critique.** The Reviewer role (never the Implementer) tries to disprove the proposal's success — adverse inputs, chunk boundaries, repeated actions, multiple seeds, save/load cycles (doc 46 §3). The critique is signed.
   525→12. **Semantic Diff.** The change is summarized in human-readable terms (doc 46 §2): "3 mountain ranges modified, 1 faction removed, 27 settlements affected, 18,421 NPC relationships recalculated." This is what the human operator reads.
   526→13. **Approval or Rollback.** The decision. If approved at the AI's autonomy level, the transaction commits; if escalation was required and not granted, the transaction rolls back. Either way, the audit log records the decision and the reason.
   527→
   528→### 6.3 Rollback semantics
   529→
   530→A rollback restores the workspace to the Snapshot. It does not partially undo — if step 8 failed, steps 2-7 are not "kept"; the entire patch is reverted. The workspace is discarded; a new transaction starts from the baseline if the AI wants to retry.
   531→
   532→The rollback **does not affect the audit log**. The audit log is append-only. A rolled-back transaction is still a transaction; its failure mode is still recorded; the lessons learned still feed the architectural decision ledger (doc 49 §3).

   536→## 7. Failure cases
   537→
   538→| Failure | Detection | Response |
   539→|---|---|---|
   540→| AI issues a tool call above its autonomy | Gateway rejects at `authorize` | `error.code = 'AutonomyExceeded'`; AI must escalate |
   541→| AI issues a tool call without a capability token | Gateway rejects at `authorize` | `error.code = 'MissingCapabilityToken'`; session may be flagged |
   542→| Gateway loses connection to engine mid-command | Heartbeat timeout (5s) | Gateway marks the command `pending` → `cancelled`; AI may re-issue |
   543→| Engine crashes during a transaction | Engine heartbeat loss | All in-flight transactions roll back to their snapshots; audit log records the crash |
   544→| AI's session expires mid-transaction | Token expiry at Gateway | In-flight transactions continue under the session's last autonomy level; new commands require re-auth |
   545→| Webhook delivery fails for >24h | Retention expiry | Event is dropped; AI reconciles by querying state on reconnect |
   546→| Deterministic replay fails | Hash mismatch | Hard fail; transaction rolls back; the audit log flags the patch as determinism-breaking |
   547→| VLM playtester reports visual regression | Frame diff above threshold | Loops back to Implement; the playtester's report is the artifact |
   548→| Reviewer refuses to sign | IndependentCritique step fails | Transaction cannot advance past step 11; loops back to Propose |
   549→| Human operator rejects the semantic diff | ApprovalOrRollback step fails | Transaction rolls back; the rejection reason feeds the decision ledger |
   550→| Gateway's audit log is full | Disk quota | Gateway refuses new commands (fail-closed); operator must rotate the log |
   551→| AI attempts to change the architect system itself | Tool whitelist | Gateway refuses; only a human operator may modify the architect system (doc 48 §3) |

   555→## 8. Rejected alternatives
   556→
   557→### 8.1 "A single AI with full access"
   558→
   559→The first design: one AI, full engine access, an audit log, and trust. Rejected for three reasons. First, the doctrine (AGENTS.md Part 3) says: "Exhibit reviewer voices; do not self-certify." A single AI that writes and approves its own work has no reviewer. Second, the blast radius of an uncontrolled mutation is the player's save — possibly hours of play, possibly a century of simulation. A single misbehaving AI with full access can destroy that. Third, the project's regulatory and ethical posture requires that a human can attribute any change to a specific role and a specific decision; a single-AI model makes that attribution trivial in theory and meaningless in practice.
   560→
   561→### 8.2 "Pure request-response, no webhooks"
   562→
   563→The second design: every event is a tool the AI polls. Rejected because polling wastes bandwidth (the AI asks "anything new?" every N seconds, the engine says "no" 99% of the time), adds latency (events arrive at the next poll, not when they happen), and produces a worse audit story (the polling call is audited as a tool call, drowning the actual events in noise). The webhook channel is the standard pattern for engine-to-listener notification; pretending it is the same as request-response produces contortions.
   564→
   565→### 8.3 "The browser channel can mutate state"
   566→
   567→The third design: the AI drives the engine by simulating clicks in the browser, which the engine interprets as commands. Rejected because (a) it makes the audit trail depend on UI element identity, which is fragile; (b) it conflates observation and control, breaking the channel separation in section 1; (c) it makes programmatic changes indistinguishable from player input, which is exactly what the determinism contract (doc 06) is trying to keep separate. The browser channel may inject input that becomes a command, but the command is recorded as a command, not as a click.
   568→
   569→### 8.4 "Three autonomy levels instead of seven"
   570→
   571→The fourth design: Observe, Sandbox, Release. Rejected per section 5.2 — the binary-ish model either under-trusts the AI (every interesting change waits for Release approval) or over-trusts it (Release becomes the default for anything touching main). Seven levels let each change progress at the lowest level that suffices.
   572→
   573→### 8.5 "The Gateway is in-process with the engine"
   574→
   575→The fifth design: the Gateway is a plugin inside the PluginHost. Rejected because (a) it couples the security boundary to the engine's lifecycle — an engine crash takes the Gateway with it, breaking audit continuity; (b) it gives the Gateway access to engine internals it should not see (the player's save, decrypted); (c) it makes the Gateway subject to the same plugin-permission model as mods, which is backwards — the Gateway should be the authority on permissions, not subject to them. The Gateway is a separate process, listening on a separate socket, holding separate secrets.
   576→
   577→### 8.6 "Skip steps for 'trivial' changes"
   578→
   579→The sixth design: the Architect role may skip Test, Simulate, Benchmark, or Critique for changes it deems trivial. Rejected because "trivial" is exactly the change class where skipping review is most expensive — the change that "obviously" cannot break anything is the change that breaks the determinism hash. The audit log may record a step as `skipped` with a reason, but the skip is signed and visible; skipping the determinism replay for a state-mutating change is forbidden, full stop.
   580→
   581→### 8.7 "Self-improvement is autonomous by default"
   582→
   583→The seventh design: the AI commits changes at the Integrate level without human approval, and only Release requires a human. Rejected for now — the project is not yet at the maturity level where this is safe (no save migration test corpus, no production-grade red team, no formal verification of the determinism stack). The doctrine (AGENTS.md Part 3) says: "Ship the working thing before the perfect thing." The working thing is a control plane where the AI does most of the work and a human signs at Integrate and Release. Autonomous Integrate is a Phase 7+ goal, not a Phase 1-6 default.

   587→## 9. What this document enables
   588→
   589→The control plane as specified here enables the canonical AI-driven workflow:
   590→
   591→1. The AI **observes** an engine subsystem (through Inspection tools, doc 44 §3).
   592→2. The AI **diagnoses** a gap (through Explanation tools, doc 44 §5, and the World Oracle, doc 49 §4).
   593→3. The AI **researches** solutions (through the research broker, doc 47).
   594→4. The AI **proposes** a change (a typed Proposal, section 4.1).
   595→5. The AI **implements** the change in an isolated workspace (doc 46 §1).
   596→6. The AI **validates** the change through the transactional process (section 6).
   597→7. The AI **presents** the semantic diff and the evidence (doc 46 §2).
   598→8. The change is **committed or rolled back**, and the decision is recorded (doc 49 §3).
   599→
   600→Each of these steps is detailed in the companion documents. The control plane is the spine; the companion documents are the limbs.
   601→
   602→The doctrine (AGENTS.md Part 3) says: "Design for joy first; the system serves the experience." The control plane is not the experience. The experience is a player playing One Mortal Morning for an hour and wanting a second hour. The control plane exists so that an AI can build, test, and refine that experience at a pace and a rigor a human team alone cannot match. The measure of the control plane is the same as the measure of the engine: does the player want a second hour?
